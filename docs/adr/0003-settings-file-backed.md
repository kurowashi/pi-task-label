# ADR 0003: 設定の正はファイルとし、変更コマンドは実測した変更頻度にだけ追加する

- 状態: 採用
- 日付: 2026-10-03
- 対象: 全リポジトリ共通の PHILOSOPHY.md(7コピーを逐語同一に更新)

## 背景

- Pi 拡張の設定をすべて Pi の UI 上で変更できるようにする案を検討した。
- Pi 本体の `/settings` はコア設定専用で、拡張が設定を登録する API はない。拡張が設定 UI を持つには、
  設定スキーマとは別に UI メタデータ、書き込み層、モード対応をプラグインごとに持つことになる。
- 拡張の設定は合計 60 キー超あり、自由形式の API ボディ(pi-exa の `defaults`)と配列(pi-jev の `rules`)を含む。
  すべてを UI で扱うことはできない。
- 対話 UI は TUI でしか使えない。RPC モードでは対話 UI API の `custom()` が使えず、
  print / JSON モードには UI がない。設定 UI はファイルの置き換えにならず、常に追加レイヤーになる。
- 変更頻度の実測はまだ無い。使用の証拠なしに UI を維持するのは、判断の手順1に反する。

## 決定

1. 設定の正はファイルとする。設定が壊れても既定値で動作する(原則5)。
2. 設定 UI は採用しない。実測した変更頻度が高い設定にだけ、
   設定を変更するコマンドを引数で完結する形で追加する。
3. 変更頻度の実測が得られるまで、設定を変更するコマンドは追加しない。
4. この設定の持ち方で解決できない問題が出たときにだけ、見直す。

## 理由

- 設定ファイルと引数コマンドは全モードで動き、テストで拘束できる。
- 維持コストは設定数に比例します。設定 UI は設定スキーマとの二重管理になり、
  設定を増やすたびに UI メタデータ、テスト、README の更新が要ります。
- 変更頻度が高い設定には、必要になった時点で引数コマンドを足せます。需要はそのときの実測で確かめられます。

## 帰結

- 設定 UI の追加は、思想の変更として扱います。
- 実測で変更頻度が高い設定への引数コマンドの追加は、この原則の下で認められます。
- この決定より厳しい制約(設定を持たない、コマンドを持たない)は、そのまま残ります。

## 代替案

| 代替 | 却下理由 |
|---|---|
| すべての設定を変更する UI を追加する | 拡張設定の登録 API がなく、モード対応と設定スキーマの二重管理が必要になる |
| すべての設定に変更コマンドを追加する | 変更頻度の実測がなく、維持コストを正当化できない |
